# UX review of the setlister UI

*Spike, 2026-07-15. Findings from an expert-lens UX review of the web app
(`ui/`), grounded in hands-on testing rather than code reading alone.*

## Method

- Read the full UI source (`index.html`, `app.js`, `style.css`, `sync.js`,
  `session-id.js`).
- Drove the real app with Playwright at a phone viewport (390×844, `isMobile`,
  `hasTouch`, `.tap()`), per the repo's own testing guidance, against the local
  API. Also checked 320×568 and landscape.
- Exercised: first run, manual add (hits and misses), scan → review → confirm
  (with a stubbed `/api/parse` response covering confirmed / needs_review /
  conflict / unmatched / crossed-out rows), corrections via the song picker,
  promote/demote, played/bin (buttons and swipes), Start over, sharing, and the
  failed-scan and hung-share error paths.
- Measured tap-target sizes and text contrast at runtime.

Severity scale: **P0** breaks a core flow · **P1** high friction / likely user
harm · **P2** moderate · **P3** polish.

## What already works well

The two-list mental model (Requests pool → Up next running order) is sound and
the empty states teach it. Swipe gestures have proper vertical-intent
detection and snap-back; remote snapshots are deferred during gestures so a
peer's edit can't yank a row mid-drag; `prefers-reduced-motion` is respected;
the scan overlay is genuinely delightful. The issues below are mostly the last
mile: error handling, discoverability, touch ergonomics, and a few real
defects.

## P0 — defects that break core flows

### 1. "Correct song…" dropdown renders underneath the next card

Each `.row-body` sets `position: relative; z-index: 1` (`ui/style.css:244`),
creating a stacking context. The picker menu's `z-index: 20`
(`ui/style.css:368`) only wins *within its own row*; the next `<li>` paints on
top of it. Reproduced in the tour: taps on options overlapping the following
card were intercepted by that card's `.row-body` (Playwright timed out
retrying), and screenshots show the menu buried under the next row. Correcting
any review row except the last is broken or misfires — and this is the app's
core recovery flow.

Fix: raise the open row (e.g. `.row-card:focus-within { z-index: 2 }`) or
portal the menu to `<body>`.

### 2. Raw backend exceptions shown verbatim to users

A failed scan displayed *"Vision model call failed: Your default credentials
were not found. To set up Application Default Credentials, see
https://cloud.google.com/docs/authentication/…"* — `app.js` prints
`err.message` straight into the error box (`ui/app.js:641-646`). A club
volunteer can act on none of that. Translate to human copy ("Couldn't read the
board — check your connection and try again"), keep the detail in a
collapsible/console.

### 3. After a failed scan, the error is off-screen and the stale photo stays

The `#error` box sits *below* the full-width photo preview
(`ui/index.html:105-116`). The page auto-scrolls to the photo while scanning,
so on failure the message renders below the fold — screenshots show a viewport
of dead photo and no visible error. The failed photo also lingers
indefinitely. Scroll to the error, or overlay it on the photo where the user
is already looking, and clear the preview.

### 4. Share button can hang forever as "⏳" — and tap-to-explore = commit

Tapping 🔗 with no session immediately *creates* one (`onShareTap`,
`ui/app.js:327-352`). If Firestore is unreachable (pub Wi-Fi), the `await`
never resolves: the button was still a disabled hourglass with no timeout, no
error, no retry. Separately, a user just curious about the icon commits to
creating a shared, anyone-with-link-can-edit session — the explanatory popover
only appears *after* creation. Add a timeout + failure message, and a
lightweight "Start sharing these lists?" step first.

### 5. Binned songs still appear in the exported list, unmarked

`exportedRows()` filters `removed` and `crossed_out` but not `binned`
(`ui/app.js:1155-1159`). Binning means "we're skipping this one", yet "Copy
list" outputs it indistinguishably from live songs. Exclude binned rows from
export, or mark them (strikethrough / "(skipped)").

## P1 — high-impact friction

### 6. Touch targets far below spec in a mobile-first app

Measured at 390px: reorder ↑/↓ **14.8×26.4px**, drag handle 18.7×23.2, bin
23.2×26.4, played/promote/demote ~27×27, "Start over" 58.9×**15**, settings
gear 38.4×38.4. Platform guidance is 44–48px. The CSS itself flags the gear as
under-spec (`ui/style.css:52-53`) but only the share button got the 44px
pseudo-element fix. Pad the hit areas of every row tool — these are used
mid-gig, one-handed.

### 7. Search that finds nothing says nothing

A query with no catalogue hit just closes the menu — no "No matches in the
songbook" row, and no way to add free text anyway (the scan flow supports
unmatched rows; manual add doesn't). Worse: `loadCatalogue`/`loadEditions`
swallow all errors (`ui/app.js:409, 427`), so if the catalogue never loaded
the search box is permanently dead with zero indication. Add an explicit
no-results state, an "add anyway" affordance, and surface catalogue-load
failure.

### 8. Match status is nearly invisible and vanishes after confirm

Confirmed (97%), needs_review, and conflict (40%) rows all get the same green
edge (`ui/style.css:258-260`); the only differentiator is a small ⚠️. "➕ Add
5 to requests" happily ingests unresolved conflicts, and once in Requests
nothing marks them — a wrong match looks exactly like a verified one.
Suggested: amber edge for flagged rows, "2 need checking" on the confirm
button, carry the flag into Requests until resolved.

### 9. The scanned photo is inaccessible for confirmed rows

`openReview()` hides the add section, which contains the preview; only ⚠️
rows expose the lightbox. If the model *confidently misread* a row (the
dangerous case) there's no way to check it against the handwriting — and after
confirm the photo is gone entirely. Add a persistent "view photo" affordance
in the review sheet.

### 10. Lightbox can't zoom, but closes on any tap

Checking handwriting on a 390px-wide photo needs pinch-zoom; the lightbox
image is capped at `max-height: 80vh` and *any* tap dismisses
(`ui/app.js:684`). Adjusting your grip closes it. Support pinch/double-tap
zoom; close only on ✕ or backdrop.

### 11. Adding a tune mid-gig requires scrolling past everything

With a realistic 23 songs, the add field sat at y≈1834 of a 3354px page — two
screens down, drifting further as lists grow. The most frequent gig actions
(add a request, see what's next) live at opposite ends of an ever-longer page.
A sticky bottom add-bar (or FAB) fixes this outright.

### 12. "Start over" reads as scoped to Up next but wipes both lists — for everyone

It sits in the Up next header (`ui/index.html:82-85`) yet clears Requests too,
and in a shared session clears them for all peers. The confirm text is honest,
but the placement teaches the wrong scope, native `confirm()` is easy to blow
through, and the app has no undo of any kind. Move it out of the section
header; consider an undo snackbar over a confirm.

### 13. Scans can't be cancelled and can double-fire

No fetch timeout or abort — the overlay animates forever if the API stalls.
The camera button stays tappable during a scan, so a second photo starts a
concurrent parse that races the first (`ui/app.js:604-649`). Disable during
flight; add cancel + timeout.

### 14. Join-by-link opens a blocking native confirm before the app paints

`resolveSession()` fires `confirm()` during init (`ui/app.js:227-237`) with
replace-only semantics — no merge, no preview of the session, decline silently
strips the param. Render the app first; use an in-page dialog that explains
both outcomes.

## P2 — moderate

15. **Settings mixes two audiences.** Name, edition, and *export* sit beside
    "Model", "Disable model thinking", "Send songbook to model", "Max image
    edge (px)" (`ui/index.html:30-75`). Volunteers shouldn't meet Gemini
    tuning to change their name; "Your name" never explains it feeds the
    "Added by" line. Split advanced scan tuning behind a divider/sub-panel.
16. **"📋 Copy list" — the end-of-night payoff — is buried in settings.**
    Deserves a visible home near the lists.
17. **Inconsistent icon language.** ↑/↓ text arrows (reorder) beside ⬇️ emoji
    (demote) in the same toolbar; 🗑 means "cross out but keep" in lists and
    "drop from scan" in review; ✓/🗑/⠿ are plain glyphs while ⬆️/⬇️ are
    colored emoji. Swipes have zero discoverability — nothing hints rows are
    swipeable.
18. **Manual adds show noise:** `wrote: "Jolene - Dolly Parton" · p.63` +
    "added manually" (`ui/app.js:791-797`) — the "wrote:" line is a verbatim
    duplicate for manual entries. Show it only for scans.
19. **Crossed-out rows: added by default, then silently dropped from export**
    (the "Include crossed-out rows" toggle defaults off). The user watches a
    struck-through row get added, then it vanishes from the copied list.
    Default crossed-out rows to removed in review (restorable), or reconcile.
20. **No duplicate detection.** The same tune via board + manual add (common at
    a gig) appears twice with no warning or merge.
21. **Played songs just fade in place.** No "7 of 15 played" progress, no
    collapse/sink of finished songs; at 0.5 opacity the row's already-small
    buttons fade too.
22. **Android users can't pick an existing photo.** `capture="environment"`
    (`ui/index.html:103`) forces the camera on most Android browsers — but
    boards are often photographed earlier or shared via WhatsApp. Offer both
    capture and gallery.
23. **Four names, no identity.** Tab: "UT Request Board Parser"; header:
    "Whiteboard of Wishes"; share sheet: "Ukulele Tuesday setlist"; repo:
    "Setlister". Also no favicon, `theme-color`, manifest, or
    apple-touch-icon — "Add to Home Screen" yields a blank generic icon.

## Accessibility

24. **iOS zoom-on-focus:** song-picker inputs are 0.9rem ≈ 14.4px
    (`ui/style.css:365`); iOS Safari zooms the viewport for inputs under 16px,
    jolting the layout on the primary platform. Make inputs ≥16px.
25. **No live announcements:** `#error` lacks `role="alert"`/`aria-live`; list
    changes and the "✅ Copied!" label flash are silent to screen readers.
26. **Focus management:** settings/share panels and the lightbox
    (`role="dialog"`, `aria-modal`) never move focus in, trap it, or restore
    it. The combobox lacks `aria-activedescendant`/`aria-controls` and its
    only label is a placeholder.
27. **Contrast/legibility edges:** `.raw`/`.added-by` are #777 at ~13px —
    borderline AA fail for small text; disabled buttons at 0.3 opacity are
    near-invisible; ↑/↓ rely on `title` alone for their accessible name.
28. **Light-only theme** (`color-scheme: light`, `ui/style.css:9`): the app is
    used in an evening pub session — a full-brightness cream screen in a dark
    room. Dark mode is a contextual need here, not a nicety.

## P3 — polish

- Settings panel (~557px tall) overflows short viewports (320×568); bottom
  fields need awkward page-scroll while anchored to the header.
- Session errors ("expired", "not found") render in the `#error` box near the
  bottom add-section, far from the share button that triggered them.
- Footer "generated 2026-07-14" is provenance jargon — easily read as the
  setlist's date rather than the songbook's.
- Model dropdown copy ("default (gemini-2.5-flash)", "thinking") assumes LLM
  literacy.
- Escape closes the settings panel even while a combobox menu is open — one
  keypress, two actions.
- No failure feedback if the clipboard write silently fails on old browsers.

## Top 5 fixes by value-for-effort

1. Picker z-index bug (#1) — one CSS rule, unblocks the core correction flow.
2. ≥44px tap targets for all row tools (#6).
3. Humanize + reposition scan errors (#2, #3).
4. Sticky add-bar / surface "Copy list" (#11, #16).
5. Empty-search feedback + catalogue-failure surfacing (#7).
